# Pragmatic-DDD Go 框架开发规范
> 定位：务实DDD，不强制EventSourcing；领域纯净，SPI基础设施可插拔，事务Outbox保障最终一致性。

## 1. 架构分层总览
分层原则：**依赖只能由外层向内层依赖，禁止反向依赖**

| 分层 | 职责 | 依赖约束 |
|---|---|---|
| 接口层(Handler/Controller) | http/rpc请求接收，参数转换，调用应用服务 | 只能依赖application |
| 应用层(application) | 工作单元编排、仓储调用、命令/查询分发；**无业务规则** | 依赖domain；不写业务逻辑 |
| 领域层(domain) | 聚合、实体、值对象、领域事件、业务规则 | **零外部依赖**，不能导入db、mq、web包 |
| 基础设施层(infra) | 仓储实现、Outbox、事件总线、防腐层ACL、ID生成 | 依赖domain，实现domain定义的接口 |
| pkg公共包 | 错误定义、特性开关等通用工具 | 可被所有层引用，不依赖业务 |

> 核心铁律：domain包不能import infra/application。领域模型可单独单元测试，不需要数据库/中间件。

## 2. DDD建模规范
### 2.1 聚合与聚合根
1. 聚合 = 事务一致性边界，**一个事务只修改一个聚合根**。跨聚合业务流程使用领域事件实现最终一致性。
2. 聚合根嵌入`domain.AggregateRoot`；子实体不能独立存在，只能通过聚合根访问。
3. 聚合内部状态**禁止外部直接读写**，所有状态变更必须调用聚合提供的领域方法（`order.Pay()`）。
4. 聚合根内置版本号，默认使用乐观锁做并发控制。
5. 聚合内部通过`CollectEvent()`收集领域事件；事件由UoW在Commit时取出。

### 2.2 值对象
1. 值对象必须实现`domain.ValueObject`接口，基于属性相等而非引用相等。
2. 值对象设计为**不可变**：字段一旦创建，不允许修改；变更直接返回新对象。
3. 适合场景：地址、金额、手机号等描述属性，无唯一ID。

### 2.3 领域事件
1. 事件不可变，嵌入`domain.BaseDomainEvent`。
2. 事件尽量轻量化：只携带聚合ID、版本号，**不要携带完整聚合数据**。
3. 事件只能在聚合内部产生，应用服务不能手动New领域事件。
4. 事件发布两种模式：
   - MemoryEventBus：单体，内存同步事件
   - Outbox + MQ：分布式，事务发件箱保证可靠投递

### 2.4 业务规则
1. 业务规则必须放在domain层，**禁止写在应用服务/handler**。
2. 规则实现`domain.BusinessRule`接口，使用`RuleValidator`校验。
3. 校验支持两种模式：failFast快速失败 / 收集全部错误一次性返回。
4. 错误统一返回`DomainRuleError`，上层统一捕获业务规则异常。

## 3. 工作单元 & Outbox规范
1. 优先使用`OutboxUnitOfWork`：聚合持久化 + Outbox消息写入在同一个数据库事务。
2. Outbox Relay后台协程做消息兜底重试，超过最大重试自动转入死信。
3. 事件投递失败：由Relay补偿，业务代码不需要手动重试事件。
4. 事务只保证本地聚合+outbox记录落库；事件消费最终一致性。

## 4. 仓储规范
1. 仓储接口定义在domain层，实现在infra层。
2. 仓储接口`Repository[T]`只操作聚合根，禁止单独操作子实体。
3. 子实体集合变更使用`persist.TrackedList`，增量更新，避免全删全更新反模式。
4. 查询模型（读模型）单独CQRS Query，不使用仓储查询复杂报表。读模型投影异步构建。

## 5. 防腐层 ACL（外部系统调用）
1. 外部第三方调用统一封装在infra/acl，隔离外部API变化。
2. 区分可重试异常与不可重试异常。
3. 外部依赖在代码显式声明，不要隐藏在业务逻辑内部。
4. ACL返回错误统一包装为`AclError`，标记是否可重试。

## 6. 应用服务编码规范
1. 应用服务只做**编排**：加载聚合 → 调用聚合领域方法 → UoW注册变更 → Commit。
2. 不写if业务规则判断，业务规则下沉到domain。
3. 使用Command模式封装写操作；Query封装读操作，读写分离。
4. 应用服务不直接操作数据库，依赖仓储接口。

## 7. 反模式黑名单（禁止）
❌ 在应用服务写业务规则校验
❌ domain包引入DB、MQ、Web框架依赖
❌ 单个事务修改多个聚合根
❌ 外部直接修改聚合结构体字段
❌ 领域事件携带大量业务数据
❌ 子实体独立仓储、单独查询
❌ 无脑上EventSourcing，仅读模型复杂才使用投影
❌ 硬编码业务错误码，使用`BrokenRule.Code`统一管理

## 8. 单元测试规范
1. **领域模型单元测试**：无需DB/Mock，直接New聚合，调用领域方法，校验规则与事件。（最高优先级）
2. 应用服务测试：mock仓储与UoW。
3. Infra层测试：依赖真实数据库/中间件，作为集成测试。
4. 测试重点：业务规则校验、聚合状态流转、事件生成。

## 9. 工程与模块规范
1. 业务模块独立，参考example/order组织代码。
2. 基础设施实现可插拔，更换数据库/MQ只替换infra层实现，domain代码不动。
3. 特性开关：使用`config.Toggle`，支持 OFF/ROLLOUT/ON 三态与白名单灰度；原始配置经`config.Source`读取、`config.Bind`绑定为类型化对象。
4. 对外广播：使用`broadcast.Subscriber`订阅领域事件，组装`broadcast.Envelope`统一信封（消息ID/聚合身份/版本/成因操作/来源事件）经`broadcast.Messenger`发往外部约定topic，与内部事件MQ链路解耦；发送失败（`SendError`）可重试，构消息/序列化失败（`EnvelopeError`）不可重试。

## 10. 扩展路线
1. 增加MySQL仓储实现、MySQL OutboxStore
2. 增加读模型投影`IAggregateProjection`，Reconciler对账修复数据不一致
3. 游标分页查询抽象
4. OpenTelemetry链路追踪埋点（事件、UoW）
